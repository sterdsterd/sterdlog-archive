# 들어가며

요즘 나는 개발 외적인 시간의 꽤 많은 부분을 "기획 다시 확인하기"에 쓰고 있었다. 이슈를 받아서 코드를 짜려고 보면, 정작 정해져 있어야 할 게 비어 있을 때가 있다. 그러면 구현을 멈추고 한 번 확인하고, 답이 오면 또 다른 빈칸이 보인다.

이걸 한동안 흐린 눈 하면서 사람 문제로 봤는데, 막상 들여다보니 그보다는 구조 문제에 가까웠다.

# 리스크가 가장 비싼 곳에서 발견된다

빈칸을 거르는 가장 싼 지점은 상류다. 문제 정의에서 한 번, 요구사항에서 한 번, 세부 기획에서 한 번. 그렇게 걸러지고 남은 것만 개발로 내려오는 게 이상적이다.

허나 지금 상황에서는 그 거름망이 자주 비어 있고, 빈칸을 처음 마주치는 사람이 제일 마지막 단계, 그러니까 코드를 짜는 사람이 되기 쉽다. 코드를 펼쳐야 "어 이거 안 정해졌네"가 보이니까. 결국 빈칸이 가장 비싼 지점에서 발견되는 셈이다.

여기 딸려오는 패턴이 하나 더 있다. 결정이 안 닫힌 채로 내려오면, 다음 단계 사람이 그 결정을 대신 내려주게 된다. 그게 한두 번이면 협업인데, 반복되면 결정의 책임이 자꾸 하류로 밀린다. 그리고 그렇게 메꿔 넣은 판단은 다음 문서에선 또 사라지기 쉽다. 사람 머리에만 남았으니까.

# 뇌를 밖으로 꺼내기

기획을 받았을 때 머릿속에서 도는 게 있다. (왜 내가?) 이거 진짜 문제 맞아? KPI 베이스라인은? 이 케이스 빠졌는데? 이건 기획에서 정할 일이지 구현에서 정할 일이 아닌데?

그래서 나의 기준을 밖으로 꺼내보기로 했다. "내가 산출물을 받았을 때 적용하는 기준"을 하나의 프록시로 만들어서, 개발로 넘어오기 전에 스스로 그 프록시랑 먼저 부딪히게 하는 거다. 통과한 것만 다음 단계로 간다. 빈칸을 거르는 지점을 상류로 옮기는 데에 의의를 뒀다.

제약을 하나 강하게 걸었다. 이 에이전트는 답을 주면 안 된다. 답을 주는 순간 결정을 에이전트가 대신 내려버려서, 그럴거면 기획자의 존재 의의가..? 그래서 얘는 질문과 옵션만 던지고 결정은 사람이 한다.

사용 환경은 Claude Code 데스크탑 앱으로 정했다. 비개발자(기획자/PM)가 써야 하니까 별도 봇 서버나 API 토큰 과금 없이, 터미널 없이 사용할 수 있는 방법 중에 가장 도입비용이 적었다. 거기에 skill과 harness를 얹는 형태다.

# 설계: 게이트 세 개와 산출물의 책임

뼈대는 게이트 세 개다.

| 게이트 | 막는 것 | 핵심 질문 |
|---|---|---|
| Gate 0 | 착수 자체 | 진짜 풀 문제인가, KPI 베이스라인은, 근본 해결인가 |
| Gate 1 | 명세 완성도 | 빈칸(TBD) 0개인가, 엣지 봤나, AC가 측정가능한가 |
| Gate 2 | 핸드오프 | SoT가 한 군데(Linear)인가, 추정, 의존성 있나 |

통과 못 하면 산출물을 만들어주지 않는다. 미통과 + 다음 질문 하나만 돌려준다. 이게 의외로 중요했는데, 안 그러면 어중간한 문서를 그냥 뱉어버리더라.

제일 도움이 된 개념은 산출물 altitude다. PRD, 요구사항, 세부기획이 자꾸 섞이길래, 문서마다 고도를 정하고 각 고도가 담아야 할 것(MUST)과 담으면 안 되는 것(MUST-NOT)을 못 박았다.

| 고도 | 문서 | MUST-NOT |
|---|---|---|
| WHY | PRD | 화면, 기능명세 |
| WHAT | 요구사항 | 화면 레이아웃, 카피, 픽셀 |
| 동작 | 세부기획 | 색/모션, 구현 알고리즘 |
| WHERE | 와이어프레임 | 비즈니스 정책 재정의 |

같은 결정은 한 altitude에만 존재하도록. KPI는 PRD가 소유하고 요구사항은 링크만 한다. 두 군데 적히면 정합성 관리를 또 해야한다.

AC(완료 정의)는 EARS + GIVEN/WHEN/THEN으로 강제했다. 자연스럽게 동작한다는 AC가 아니다.

```
WHEN 당일 첫 문항 풀이가 완료되면 THE SYSTEM SHALL streak을 +1 한다
GIVEN streak이 6일이고 어제 학습 안 함 / WHEN 오늘 첫 진입 / THEN 초기화 팝업 1회
```

누가 봐도 통과/실패가 같게 떨어지는 문장. 이게 안 되면 미결로 본다.

# 구현: constitution 하나와 스킬 몇 개

플러그인 구조는 생각보다 단순하다. 핵심은 `constitution.md`라는 불가침 규칙 한 장이고, 모든 스킬이 동작 전에 이걸 먼저 읽는다. constitution과 개별 스킬이 충돌하면 constitution이 이긴다.

규칙은 이런 식이다.

> 1. 답이 아니라 질문. 결정을 대신 내리지 마라.
> 3. 모호함은 버그. TBD, "미정", "~할 수 있음"을 완료로 인정하지 마라.
> 5. 칭찬은 아껴서. 분량으로 칭찬하지 마라.

스킬은 의도별로 쪼갰다. 진입(dispatcher) → 문제 심문(problem-gate) → 분해 코칭(spec-coach) → 기존 문서 린트(doc-lint) → 이슈화(linear-ops). 문서 골격은 처음엔 공통 템플릿 하나로 뭉쳤다가, 나중에 타입별(PRD/요구사항/세부기획)로 쪼갰다.

# 캘리브레이션

뼈대 만드는 건 며칠이면 된다. 진짜 시간은 튜닝에 들어갔다. 직접 기획자처럼 입력을 넣어보면서 계속 고쳤다.

1트 — 말투. 처음엔 얘가 자기 사고 과정을 그대로 토했다. "Gate 1을 통과하려면 6+1 렌즈로 봤을 때…" 이런 식. 쓰는 사람 입장에선 뭔 소린지도 모르고 끌려가는 느낌이다. 그래서 내부 용어(게이트, 렌즈, 고도)는 속으로만 쓰고, 화면엔 "왜 아직 안 되는지 짧게 + 다음 질문 하나"만 나오게 막았다.

2트 — 칭찬에 인색하기. 무난한 문서에도 "꼼꼼하네요"가 잘 나왔다. 칭찬이 기본값이면 기준이 내려간다. "정말 높은 기준 넘었을 때만, 한 일 자체를 구체적으로"로 바꿨다.

3트 — 범위가 자꾸 커진다. 기능 얘기는 자연히 커지는 경향이 있고, 양보되는 기능이 잘 안 나온다. 그래서 기능을 더하자는 얘기가 나오면 항상 두 개를 되묻게 했다.

- "왜 그 수준이어야 하나? 그 레퍼런스 앱은 그게 본업이라 그런 건데, 우리도 본업인가?"
- "더하는 만큼 뺄, 미룰, 안 할 건 뭔가?" (비목표가 비면 미결로 본다. 우선순위는 버린 걸로 증명된다.)

4트 — 템플릿이 안 쓰였다. 분명 템플릿을 만들어놨는데 잘 안 쓰였다. 까보니 두 가지였다. 하나는 스킬이 참조하던 템플릿 파일이 실제로는 없었다(죽은 참조). 다른 하나는 공통 템플릿 하나가 모든 문서를 커버하려다 보니 기준이 너무 약했다. 칸 이름만 있고 합격선이 없으니, 한 줄 대충 채워도 채워진 것처럼 보였다.

그러다 발견한 건데, 와이어프레임에까지 KPI 칸이 들어가 있었다. 화면 설계한테 KPI를 적으라는 셈이다. 다른 데선 막는 altitude 위반을 정작 템플릿이 저지르고 있던 거다. 그래서 공통 하나를 버리고 타입별로 쪼갰다. 각 문서가 자기 고도의 합격선을 직접 들고 있게. 공통 템플릿은 "그 외 문서"용으로만 남겼다.

# Code Graph: 여러개의 프로덕트 레포를 한 장의 그래프로

마지막으로 붙인 게 code graph다. 영향 범위, 구현 가능 여부, 대략 공수 같은 질문에 답하려면, 코드를 관계로 볼 수 있어야 했다.

노드와 엣지는 이렇게 잡았다.

| 노드 | 엣지 |
|---|---|
| Screen ,  Component ,  API ,  Service ,  DB | renders ,  calls ,  handles ,  persists |

화면이 컴포넌트를 `renders`하고, 컴포넌트가 API를 `calls`하고, API가 서비스를 `handles`하고, 서비스가 테이블에 `persists`한다. 이걸 따라가면 "화면 하나 → 결국 어느 테이블까지" 경로가 한 줄로 나온다.

문제는 프론트랑 백이 레포도 다르고 언어도 다르다는 거였다. 그래서 두 그래프를 따로 만든 다음, OpenAPI 경계로 이어붙였다. 프론트의 `calls` 엣지가 가리키는 게 `GET /submissions/{id}` 같은 `METHOD path`이고, 백엔드 핸들러도 같은 `METHOD path`를 갖는다. 이 문자열을 조인 키로 써서 두 레포를 하나의 그래프로 합쳤다. 언어가 달라도 HTTP 경계는 공통이니까, 거기서 만나게 한 거다.

빌드는 정적 분석이다. 각 레포를 파싱해서 노드/엣지를 뽑고 `graph.json` 하나로 발행한다. v1에선 이걸 플러그인에 정적 파일로 동봉하고 스킬이 직접 읽게 했다(별도 서버 없이 제일 가벼운 형태). 신선도가 문제되면 다음 단계에서 CI에 붙여 머지 때마다 갱신하고, 더 가면 그래프 자체를 MCP로 띄우는 그림이다.

쓰임새는 기획 문서의 "영향 범위" 칸을 자동으로 채우는 거다. 어떤 기능을 건드린다고 하면, 그 화면에서 출발하는 경로를 따라 닿는 API, 서비스, 테이블을 펼쳐서 보여준다. 솔직히 큰 기대는 안 했는데 생각보다 잘 됐다. 공유 Submission 경로 하나를 건드리는데 서비스 17개, 테이블 20개로 퍼지는 fan-out 같은 걸 실제로 잡아냈다. 코드를 안 열고도 "이거 생각보다 큰 작업이다"가 나오는 거다.

# 그래서 잘 돌아가냐고요?

> 현재 게이미피케이션 관련 기획사항들 모두 개발 완료하는데 각 태스크별로 공수가 얼마나 들어?

```
게이미피케이션 관련 항목이 Linear에 어떻게 올라와 있는지부터 실제로 확인할게. code graph도 같이 본다.

  Ran 1 shell command

Linear에서 게이미피케이션 관련 항목을 실제로 찾아볼게.

  Called plugin:linear:linear 2 times

"게이미피케이션"이라는 단어로는 거의 안 잡혀. 실제 게임화 기능 단어들로 다시 찾을게.

  Called plugin:linear:linear 4 times

"Gamifying" 프로젝트가 있네. 거기 항목 전체를 가져올게.

  Called plugin:linear:linear, ran 2 shell commands

확인했어. "Gamifying" 프로젝트에 77개 항목이 올라와 있고, 게임화 기능들(연속학습 Streak·Special Streak·Streak 초기화·문제 풀이 피드백/보상·앱 진입 독려)이 들어 있어. 그걸 다 봤고, 코드 쪽도 대조했어.

결론부터 — 지금은 태스크별 공수를 내가 적어줄 단계가 아니야. 두 가지 때문이야.

1. 확정 공수는 개발이 매기는 숫자고, 지금 그 칸이 전부 비어 있어.
올라온 개발 티켓(BE 8건쯤 · FE 8~9건쯤)에 추정값이 하나도 안 들어가 있어. 아직 아무도 안 매긴 상태라, 내가 대신 채우면 근거 없이 지어낸 숫자가 돼.

2. 더 큰 문제 — 견적을 낼 수 있을 만큼 기획이 안 닫혔어.
이 기능들은 지금 앱(코드)에 아예 없는 신규 작업이야. 스트릭·문제풀이 피드백·진입 독려 전부 새로 만드는 거고. 그런데 정작 개발이 보고 견적 낼 화면이 비어 있어:
- 세부 화면설계서 4건이 아직 시작도 안 됨(Todo) — 연속학습 Streak / 문제 풀이 보상 / 홈 Streak / 진입 독려
- 요구사항·세부기획서는 In Review(검토 중, 확정 아님), PRD는 Canceled 상태

화면이 안 그려진 기능은 FE가 "이 화면 며칠"을 낼 수가 없어. 그래서 순서가 공수표가 먼저가 아니라, 견적이 가능한 상태를 만드는 게 먼저야. 굳이 지금 숫자를 뽑으면 스펙 바뀔 때마다 다시 뒤집힐 거고.
```
